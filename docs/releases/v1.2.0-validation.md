## Protocol and product boundaries

- DTF1 is a Dev Toolbox protocol layered on the low-level RaptorQ codec, **not wire-compatible with the RaptorQR demo**. Each frame repeats bounded metadata, a random 128-bit file ID, SHA-256 of original file bytes, a 384-byte source symbol (4-byte RaptorQ payload ID included separately) and CRC-32. One source block is sufficient within the 5 MiB cap; unsupported blocks and out-of-range ESI are rejected before WASM allocation. Zero-byte files encode one padding byte but reconstruct/hash the empty original.
- Sending: up to 8 files / 10 MiB total, 5 MiB per file, no backend/upload/network link between devices. Batches loop at target 3/6/10 FPS with recovery frames. Sender status reports playback, not receiver completion. Larger files can take considerable time; no measured optical throughput is claimed.
- Receiving: up to 3 active sessions and 8 active/completed files / 10 MiB of file contents; codec/pixel/QR working memory adds overhead. Completed IDs/count/bytes survive a receiver Worker restart through UI metadata seeding. Clearing releases all results and allows re-reception. Native decoders, tracks, Workers and object URLs have explicit owners.
- Stop/restart retains pending files. Mode changes/navigation/reload/draft-clear remounts release the tool's file state. Backgrounding stops the camera; the user explicitly restarts. File handles, file bytes and download URLs are excluded from drafts; sender speed/size options may follow normal draft settings. Compressed-file handoff is one bounded File in tab memory, consumed once, expires after five minutes and never enters the URL/localStorage.
- The receiver verifies length and SHA-256 before exposing a blob. This detects integrity, not sender authenticity. Name sanitation removes path/control characters and preserves valid Unicode within 255 UTF-8 bytes. Only raster PNG/JPEG/WebP/GIF/AVIF/BMP are previewed through `<img>`; all other types, including HTML/SVG/PDF/video, are download-only with `application/octet-stream`.
- Camera access requires HTTPS/localhost, browser support and explicit permission. Enumeration follows the permission grant; users can select another camera while stopped. Real device camera/lighting/focus behavior remains hardware-dependent.
- Offline availability requires an online PWA install with storage retained. Production precache contains both local WASM assets and the transfer Worker. The readiness label checks these versioned WASM cache entries; private browsing, eviction or a failed install may require loading online again.

## Review and validation

Four focused self-review passes: (1) protocol/allocation/integrity, package APIs/licenses and actual QR decoding; (2) camera/Worker generations, cancellation/restart, file ownership, compressor handoff, downloads, localization and narrow layout; (3) native Chrome visual inspection, shared action styles, bilingual picker and both-theme contrast; (4) main-CI failure logs, image-load/pixel-sampling harness and failure-artifact retention. Q-03 was found by reading the published scanner implementation; Q-04/Q-05 corrections came from lifecycle/state review. The first camera harness failed to paint an initial video frame and ran media overrides on insecure about:blank; those were test-harness defects and were corrected, not reported as app failures. Navigation cleanup assertions wait for the React transition rather than assuming click completion equals unmount completion.

Acceptance results and exact candidate/merge/deploy identifiers are recorded below and in the release PR. Physical PC→iPhone, iPhone→PC and Android optical transfers, camera permissions in Safari/Firefox, real lighting/focus tolerance and hardware throughput have **not** been measured. Chromium video-stream simulation exercises actual generated QR pixels, video playback, capture, the bundled ZXing/RaptorQ Worker and saved file bytes; it does not substitute for physical-device acceptance.

Local Node.js 22 checks passed: lint with zero errors/warnings, TypeScript/Vite/PWA build, 479 unit tests in 21 files, all 74 production Chromium E2E tests and dependency audit with zero advisories. The final IEC-unit and visual-control adjustments were rebuilt and verified against the full browser suite. Production precache contains 132 entries (about 2.6 MiB), including the 70 KiB transfer Worker and both separate WASM assets; the existing approximately 789 KiB entry-chunk warning remains visible.
