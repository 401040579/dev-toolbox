# v1.3.0 QR throughput validation

Baseline: `b702fd3a774351c46859f739cdee80df7d81de07` (clean main, v1.2.0). Scope: accelerate the requested screen/camera file transfer, retain the existing bounded protocol and lifecycle behavior, and distinguish payload rate from verified file throughput. Root implementation/self-review only; no independent reviewers or delegated agents.

## Protocol, compatibility and performance contract

DTF1 retains the 384-byte symbol and M-level QR profile; the new receiver accepts old senders. High-density senders use DTF2 (the same bounded metadata layout with advertised geometry), so both endpoints must update for those profiles. DTF2 allows four-byte-aligned symbols between 384 and 2800 bytes, with source/repair count and native transport size derived from the validated geometry. Filename/MIME bounds, file identity, CRC, length/SHA-256, zero-byte padding, source-block/ESI checks, native frees, deduplication and 5 MiB/file, 8 files/10 MiB/batch, 3 active-session limits remain in force. Same-ID mixed geometry/metadata is ignored. No compression or custom/color barcode is introduced.

High speed is the fresh default: four codes, 30 FPS, 1536px requested board size. Extreme uses V40-L; Compatibility resets to one code, 6 FPS and 512px. FPS and size use versioned draft fields so an old 6 FPS/512px draft does not silently limit the new default. Profile and parallel-code changes require stopping/re-preparing; speed and size can change while playing. A final partial board has fewer codes and blank remaining slots; no duplicate padding inflates useful throughput. Each tile retains a four-module quiet zone. Normal/full-screen boards fit within 60/70% of viewport height; the app warns when displayed modules are smaller than three CSS pixels.

Theoretical payload ceilings at four codes/30 FPS and short metadata are 187.5 KiB/s (High speed) and 328.1 KiB/s (Extreme); the old default is 2.25 KiB/s. These include recovery/repeated symbols, omit camera losses and are not promised file speeds. Long metadata reduces payload. Display FPS and camera processed-FPS/symbols include repeated exposures; native decode timing includes frame scanning and codec work. The verified-file rate excludes camera startup but includes pauses, missing/repeated frames and the final SHA check. The browser test's wall-rate includes startup and the UI update after completion.

Capture requests 1920×1080/60 FPS as browser ideals, never hard requirements. Pixel dimensions are capped at 1920 on each axis; camera/RGBA/native working memory is additional to file limits. Only the latest observed video frame is used, never an unbounded queue of stale pixels. Video-frame callbacks, fallback RAF, readiness timers, scan deadlines, camera tracks, Workers and Blob URLs retain explicit cancellation owners and generation checks. Saved metadata continues to seed completed IDs/capacity after a fatal Worker restart. Native vector/pixel allocations are released on every scanner pass, including errors.

## Sources and implementation choice

Primary references: [RaptorQR sender](https://github.com/infrost/RaptorQR/blob/master/apps/web/src/app/routes/sender.tsx), [receiver](https://github.com/infrost/RaptorQR/blob/master/apps/web/src/app/routes/receiver.tsx), [Worker pool](https://github.com/infrost/RaptorQR/blob/master/apps/web/src/lib/qr_worker_pool.ts), [animated_data_qr_js](https://github.com/ymuichiro/animated_data_qr_js), [standard QR versions](https://www.qrcode.com/en/about/version.html) and the installed ZXing options/API. Their buffering, parallel-symbol and video scheduling approaches informed this implementation. No upstream app/core source was copied. The existing qrcode renderer measured approximately 4.1 ms/code at V30 and 7.0 ms/code at V40 on this desktop in a separate encoding-only experiment; that excluded rendering, capture and decoding. Bounded pre-rendering met the target without another renderer/WASM dependency. Existing pinned RaptorQ/ZXing assets and notices are unchanged.

RaptorQR's public lab figures and our synthetic results are evidence of feasibility, not a phone guarantee. Physical PC/iPhone/Android optical transfer, rolling shutter, focus/lighting tolerance and Safari/Firefox camera behavior remain unmeasured.

## Review and validation evidence

Focused root self-review: (1) metadata/QR capacity, native geometry, old protocol, memory/integrity; (2) buffering/RAF/video scheduling, throughput accounting and cancellation; (3) actual native Chrome bilingual controls and simulated four-code layout, pause/resize, narrow layout, cache upgrade; (4) repeated-loop/camera cadence, deterministic loss regression and bounded rotation fix. Review found and corrected H-02, the initial extra frame wait in H-04, rate-boundary accounting in H-05, normal-window board fit, and H-06. No independent review is claimed.

One two-code UI assertion initially paused the untouched default 300×150 canvas because its ratio was already 2; it then expected a rendered-size change. The harness now waits for an actual dense canvas width above 1000 before pausing. The correction retains a stable-pixel pause assertion and resize/restart checks. Native Chrome cannot choose the fixture through its extension without file-URL permission; permission was not expanded. Its controls/localization were inspected, and isolated Chromium tests performed the full file/camera/download path.

Validation before release: Node 22 lint/build/audit passed (zero advisories), all 487 unit tests in 22 files passed, all 77 production E2E passed before the final layout/aliasing adjustments, and all nine affected E2E plus all 26 QR units passed afterward. Linux PR/main CI runs the complete final suite; its results are retained in the PR records. The existing entry-bundle size warning remains visible.

The actual v1.2.0 site ZIP upgraded in one origin/context through the Chinese update button to `/assets/index-9cj70-Du.js`; all 11 categories/descriptions and 89 tool cards remained Chinese, JSON Diff exported its full report, and the new sender/receiver engines started after a cold offline tool visit.
